# Exact unchanged-tree checkout completion

An explicit retained command whose named workspace retains identical checkout
tree terms and conflict labels MAY complete only its native checkout operation
pointer. The owning provider MUST verify an exact publication proof, current
candidate selection, original saved checkout/policy/binding and a fresh trusted
physical guard before capturing an installation-private checkout witness. That
bounded canonical witness MUST bind the original retained key/recovery digest,
original checkout bytes/fingerprint and exact candidate/physical selection. The
runtime must durably retain it with the original request before updating any
checkout bookkeeping; capture itself performs no update.

Completion holds the existing foreground lease and worker admission, checks the
guard before and after synchronized atomic native checkout replacement, and
leaves physical files, ignored/untracked obstacles and tree-state bytes
unchanged. Pinned native protobuf decoding/encoding MUST preserve the workspace
name and reject unsupported/noncanonical fields. A metadata-only pointer update
cannot authorize a changed checkout tree or generalize to tree-changing
commands.

Same-request retry accepts only the saved original state or exact intended
candidate checkout bytes. It validates all unchanged policy/tree/binding inputs
without normalizing any other field. Already selected bytes remain intact and
are synced; interruption after pointer selection cannot generate a replacement
command or repeat physical writes. A later CLI checkout, changed physical guard,
replaced binding or unrelated metadata fails explicitly. The resulting owned
proof binds original preparation, witness and physical selection, and attests
only this unchanged-tree provider boundary. Durable runtime journal composition,
tree-changing checkout and complete command transport remain separate gates.

Runtime unchanged-tree execution stores the exact private checkout witness in
the original request journal before completion. Read-only witness linkage
accessors carry key/recovery/candidate/physical identity without granting
execution. Provider-only publication and checkout proofs must match those
identities before runtime receipt acknowledgement. Historical completed/retired
retry never opens a provider, rescans physical files or reexecutes the
candidate. Tree-changing checkout and combination selection still require their
owning engines.

An original retained Prepared request MUST survive source operation/index loss
on first apply. Resolve current registration first, then restore the exact
original archive, extras and indexes under its foreground lease before reading
source-backed policy. Revalidate the actual code, combination and physical
selection after restoration; new editor changes or stale/missing combination
state cannot publish or reset the request. Revocation cannot restore source
records, and terminal receipts remain historical even after later source loss.

Before creating a retained candidate head, including retry of an unpublished
PublicationUnknown request, current trusted immutable heads MUST be checked
against the exact retained source view's visible parent ancestry. A newly
protected commit or ancestor, unrelated boundary or duplicate/oversized policy
input fails without publication or checkout; no new candidate is prepared.
Already-selected original publication is historical: recovery MAY acknowledge it
and complete guarded checkout after current policy changes, but MUST NOT create
or reannounce a candidate if that publication is no longer selected. Bounded
policy/status work retains the original foreground lease and admission through
worker exit; neither informational status nor policy validation is a publication
proof.

Known Published receipts always require acknowledgement-only recovery before
checkout, including the boundary before witness persistence. Current selection
loss cannot reauthorize publication; the receipt remains historical and pending.
